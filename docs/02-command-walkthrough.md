# 2. 从命令记录解释等待

本文件解释 `results/first_round/` 的实际运行记录，所有时间均为模型时间 ns。参数来源与缺失项见 [资源契约](01-resource-contract.md)。这里的 ns 不是真实硬件测量。

## 2.1 只访问一个 pseudobank，每次换行读 32 B

来源：[same_pb_new_rows.jsonl](../results/first_round/micro_traces/same_pb_new_rows.jsonl)。

| 时间/区间 | 实际事件 | 此时为何不能完成下一次换行访问 |
|---|---|---|
| 0–4 | 发送 ACT，4 时执行 | 行地址尚在传输 |
| 4–20 | 等待 tRCD=16 | 本地感测尚未达到本模型的 READ 条件 |
| 18–20 | 同时发送 READ，20 时执行 | 命令传输可以与前一过程尾部重叠 |
| 20–36 | 内部读取一个 32 B 原子 | 本地源端路径占用；行须保持有效 |
| 36–52 | 自动 PRE，等待 tRP=16 | 原位线域不能重新激活 |
| 36–52 | 同时将已读出数据经出口返回 | 预充电和这段外部数据传输可重叠 |
| 48–52 | 发送下一条 ACT | 数据/预充电尚未结束，但命令到达时才执行 |
| 52 | PRE 完成，下一条 ACT 执行 | 所有本轮共享/时序约束满足 |

相邻 ACT 执行于 4、52、100 ns，间隔 **48 ns**。这没有违反 tRC=45 ns；45 是必要下限，当前读出与关闭序列给出更紧的 16+16+16=48 ns 限制。

这解释了为什么本模型两个 pseudobank 的 32 B 理想交替能力为 `2×32/48 = 1.333 GB/s/grain`，而不是只算 `2×32/45 = 1.422 GB/s/grain`。前者依赖明确写出的 source/read-hold 抽象；不能宣称论文实际硬件必然具有 48 ns 这一间隔。

## 2.2 两个 pseudobank，各开一行读 64 B

来源：[two_pb_overlap.jsonl](../results/first_round/micro_traces/two_pb_overlap.jsonl)。两个区域使用不同且不相邻的 subarray。

| 执行时间 | PB0 | PB1 | 共享数据出口 |
|---|---|---|---|
| 4 | ACT row0 | — | 空闲 |
| 8 | 感测 | ACT row0 | 空闲 |
| 20 | 第一次 READ | 已激活，等源端选择 | 空闲 |
| 36 | 第二次 READ | 等共享源端路径 | PB0 第一个原子开始返回 |
| 52 | 开始 PRE | 第一次 READ | PB0 第二个原子开始返回 |
| 68 | PRE 结束并 ACT row1 | 第二次 READ | PB1 第一个原子开始返回 |
| 84 | row1 第一次 READ | 开始 PRE | PB1 第二个原子开始返回 |

52–68 ns：PB0 预充电，PB1 读出，出口正在传 PB0 已准备好的数据。三者能够重叠，不能合称“bank 忙”。从 36 ns 起，此短记录的出口开始时间为 36、52、68、84、100、116 ns，间隔 16 ns。

## 2.3 看起来空闲的另一个区域，为何仍不能激活

来源：[same_sa_conflict.jsonl](../results/first_round/micro_traces/same_sa_conflict.jsonl)。请求 0 是 `(grain0,PB0,SA0,row0,64B)`；请求 1 是 `(grain1,PB1,SA0,row1,32B)`。两个 grain 属于同一物理 bank。

请求 1 的局部状态最初为空闲，但要求共享 subarray 的另一行，必须等请求 0 关闭。记录中：

- 请求 0 的 ACT 于 4 ns 执行，两个 READ 分别于 20、36 ns 执行。
- 52 ns 开始 PRE，68 ns 完成。
- 请求 1 的 ACT 从 64 ns 传输，到 68 ns 才执行。

等待来自已有行控制共享契约。增加行命令线不会让这两个不同行合法地同时打开。相反，单元测试中改成同一 subarray **同一行**时允许重叠，避免把原文限制误写成任何跨 pseudobank 同 subarray 访问都禁止。

## 2.4 组合对照究竟支持什么

数据来源：[summary.csv](../results/first_round/summary.csv)、[runs.json](../results/first_round/runs.json)。各列为整个 8-grain 组；输入没有真实应用缓存，其他命令组为空闲边界条件。

| 每次 ACT 的有效读取量 | base 中段 GB/s | C | D | CD |
|---|---:|---:|---:|---:|
| 32 B | 8.000 | 10.667 | 8.000 | 10.667 |
| 64 B | 15.604 | 16.000 | 15.604 | 16.000 |

中段是按时间排序的中间一半返回事件统计；完整有限运行包括启动与排空，分别见报告，不能混用。

32 B 下，在默认 **ACT 传输 4 ns 假设**中，一条行接口的服务上限是每 4 ns 一次 ACT，乘 32 B 等于 8 GB/s。base 实际中段正好触及它。C 解除了这一限制后，10.667 GB/s 与本模型 8 grain×两个 pseudobank×32 B/48 ns 的行过程上界相符。

64 B 下，一条 ACT 命令支持两次 READ。默认行命令能力、列命令能力和出口总能力均允许 16 GB/s。C 版本中段达到这个值，base 为 15.604 GB/s。base 的剩余差距包含该贪心调度器的排程效果，不能据此声称 FGDRAM 硬件不可能达到 16 GB/s，更不能把 C 的小幅差值视为必需的物理改造收益。

D 在这组输入没有收益。源端每 grain 最多每 16 ns 准备一个原子，原有出口也刚好每 16 ns 发送一个原子；该组运行没有显示可被借用出口解决的持续失配。这个结果只针对当前映射、输入、范围和缓冲条件，不能否定所有网络或与 A 的交互；A 尚未合法定义。

最能说明问题的一点是：32 B base 的 `row_state_occupied` 等待累计量高于 `row_command_bus`，但 C 干预仍使吞吐上升。队列中很多未来请求等在同一行状态之后，会放大前者的 candidate-ns；等待次数/时长的排序不能直接替代吞吐因果实验。

## 2.5 缺失参数足以改变结论的量级

把 ACT 传输从假设 4 ns 改成假设 6 ns，32 B 和 64 B 的命令上限分别变成 5.333、10.667 GB/s。实际有限运行结果分别约 5.292、10.557 GB/s。两者均满足原文“超过 2 ns”的描述，因此 **论文只给出的这句话不足以唯一确定吞吐**。

2 返回槽和显式 PRE 的实验也都保留在结果中。4 槽不是对真实产品容量的确认：本模型从开始发送 READ 就预留槽位，延迟流水中 2 槽会额外引入气泡。全 die 激活窗口的短压力测试检查跨命令组禁止超发，但不能校准原文未明确的真实供电范围。

## 2.6 本轮结论

已经得到的是：**在这份公开、可复查的资源契约下，32 B 输入首先触及行命令吞吐；解除后受本模型的行访问/读出/预充电序列约束；64 B 提高每次 ACT 的有效读取量后接近或达到出口能力；D 无可见收益。**

还没有得到的是：真实 embedding 的瓶颈、新增 A 的收益、现代 3D 的面积/能量优势，或者 FGDRAM 精确复现。下一步应补齐缺失协议/电路证据；当前不能据此启动新的架构主张。
